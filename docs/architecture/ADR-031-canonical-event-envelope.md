# ADR-031: Canonical Event Envelope

## Context
A distributed system requires a rigid, predictable payload structure to handle synchronization, conflict resolution, and backwards compatibility safely.

## Decision
We establish the **Canonical Event Envelope** for all Sync API boundaries.

### The Contract
Every REST/WebSocket payload traversing the network must conform exactly to this structure:

```json
{
  "event_id": "uuid-v4",
  "event_type": "ResponsibilityCompleted",
  "schema_version": 1,
  "aggregate_id": "responsibility-uuid-v4",
  "device_id": "registered-device-uuid",
  "user_id": "user-uuid",
  "logical_timestamp": 1715000000, 
  "payload": {
    "confidence_score": 100,
    "evidence_uri": "path/to/evidence"
  },
  "signature": "base64-encoded-rsa-signature"
}
```

### Definitions
* `logical_timestamp`: Derived from the `TrustedClock`. Used for Last-Write-Wins (LWW) conflict resolution (`ADR-027`).
* `signature`: Cryptographic signature of `event_id` + `logical_timestamp` + `payload` generated by the device's Secure Enclave Private Key (`ADR-028`).
* `schema_version`: Used for forward-compatible translation (`ADR-029`).

## Consequences
* The backend (`SyncProtocol`) is decoupled from the specific `payload`. It can route, store, and verify events purely based on the envelope.
* Enforces strict immutability and audibility for every mutation.
