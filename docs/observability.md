## 1. Introduction & Observability Principles

To run LifeCircle OS as a high-reliability, 50-year system, we must be able to diagnose failures, monitor latency, and track product health. 

Our telemetry operations are guided by the following principles:
* **Traceable Context:** Every transaction, background job, and synchronization task carries a unique identity across system layers.
* **Separation of Concerns:** Observability services operate out-of-band to ensure monitoring components do not degrade core performance.
* **Strict Privacy Isolation:** Logs and metrics track system performance and aggregate business events. Telemetry **MUST NEVER** collect personal content, names, specific medicine names, bill balances, or descriptions.

## 2. Observability Tooling Stack

LifeCircle OS implements a standardized OpenTelemetry-based monitoring stack:

```
┌────────────────────────────────────────────────────────┐
│             OBSERVABILITY TOOLING PIPELINE             │
├────────────────────────────────────────────────────────┤
│   OpenTelemetry SDKs (Trace, Metric, Log collectors)   │
│                        │                               │
│                        ▼                               │
│   Prometheus (Metrics) ──► Grafana (Dashboards)       │
│   Jaeger / OTel Collector (Distributed Traces)         │
│   Sentry (Sanitized Crash & Exception Logs)            │
└────────────────────────────────────────────────────────┘
```

* **OpenTelemetry (OTel):** Standardized instrumentation APIs compiled into the FastAPI server and Flutter client to collect traces, metrics, and logs.
* **Prometheus:** High-performance, time-series database storing system performance and business metrics.
* **Grafana:** Visualization dashboard displaying resource utilization, latency, and operational health.
* **Sentry:** Real-time error monitoring and exception tracking, sanitized at the client/API gateway boundary to strip personal parameters.

## 3. Distributed Tracing & Correlation Standard

Every transaction across the LifeCircle OS network carries standard metadata context:
* **Correlation ID:** A unique string generated by the client or API Gateway for a user action, mapping the complete path of a request across all micro-services, message queues, and databases.
* **Trace ID:** Standard OpenTelemetry identifier tracing execution context.
* **Audit ID:** Logged for administrative actions (e.g., changes to family permissions or billing settings) to maintain an immutable security trail.

### Structured Logging Format (JSON)
All logs emitted by backend services must follow a structured JSON schema:

## 4. Telemetry Modeling Frameworks

Every production service and infrastructure component must be instrumented against standard operational monitoring frameworks:

### Golden Signals Framework
Mandatory for every production service. We monitor Google SRE's four core operational attributes:
* **Latency:** Time taken to service a request (split by read/write queries).
* **Traffic:** Measure of system demand (HTTP requests/second, job queue throughput).
* **Errors:** Rate of requests that fail (HTTP 5xx codes, RabbitMQ dead-letter queues).
* **Saturation:** Measure of system resource constraints (database connection pools, thread utilization).

### RED Metrics (API Services)
API endpoints track:
* **Rate:** Number of incoming requests per second.
* **Errors:** Number of requests failing to complete successfully.
* **Duration:** The time taken for requests to return responses.

### USE Metrics (Infrastructure Layer)
Resources (VMs, database instances, broker queues) track:
* **Utilization:** Average active resource consumption (CPU, Memory, Disk bandwidth).
* **Saturation:** Backlog of work waiting to be processed (run-queue length, IO wait, database queue depth).
* **Errors:** Frequency of system-level hardware or filesystem errors.

## 5. Service Level Objectives & Error Budget Governance

We establish quantitative SLIs/SLOs to govern reliability and release gates:

### Service Level Objectives
* **Availability SLO:** 99.95% API uptime per calendar month.
* **Latency SLO:** P95 latency < 300ms, P99 latency < 700ms.
* **Sync SLO:** 99% of sync events processed within target windows (Medicines < 5s, Bills/Tasks < 10s).

### Error Budget Governance
* Error budget is defined as the maximum allowed failures (e.g., 0.05% for availability).
* If a service consumes its monthly error budget, **feature deployments are frozen** immediately. Engineering resources are diverted exclusively to resolving stability and reliability issues until the budget is restored.

## 6. Observability as Code

To prevent configuration drift and ensure dashboard reproducibility:
* **Declarative Infrastructure:** All Grafana dashboards, Prometheus alert rules, SLO definitions, and operational runbooks must be defined in code and version-controlled in the Git repository.
* **No Manual Modifications:** Direct configuration modifications via Grafana or Sentry UIs are strictly prohibited.
* **Synthetic Monitoring:** Automated synthetic check scripts are scheduled, versioned, and executed as code.

## 7. Performance & Reliability Practices

### Mobile Performance Principles
The client UI adapts gracefully to hardware capabilities. We target:
* Zero dropped frames during scrolls and screen transitions.
* 60 FPS rendering baseline.
* Native 120Hz support on high-refresh-rate screens.
* Sub-100ms UI interaction feedback response times.
* Battery-efficient rendering loops (active battery drain < 3% per hour).

### Reliability Verification Practices
Continuous verification validates resilience:
* **Chaos Engineering:** Failure injection exercises (e.g., stopping active Redis nodes or blocking RabbitMQ queues) occur regularly in staging.
* **Game Days:** Monthly simulation runs mimicking network partitions and database failovers.
* **Verification Drills:** Quarterly verification drills of database restores, offline synchronization sync-merges, and mobile recovery keys.

---

## 8. Telemetry Retention & Cost Policies

To manage cloud costs and storage footprint under sustainable margins:
* **Telemetry Retention Policy:**
  * **System Metrics:** 18 months.
  * **System Logs:** 30 days.
  * **Security & Audit Logs:** 7 years.
  * **Distributed Traces:** 14 days.
* **Adaptive Sampling:** Trace collectors use tail-based adaptive sampling (capturing 100% of errors/anomalies while sampling down successful HTTP GET requests) to keep telemetry costs low.

---

## 9. Privacy-Preserving Telemetry

* **Metadata Caching:** Only operational metadata may be buffered offline in the Isar database.
* **Zero User Content:** No personal information, names, medicine names, financial amounts, or family identifiers shall ever enter telemetry pipelines.

---

## 10. Institutional Observability Principle

> **Core Philosophy:**  
> Every production event must be explainable, traceable, and reproducible. Systems must remain completely understandable. Unknown failures are institutional failures.
