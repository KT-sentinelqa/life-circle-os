# SEC-001.5: Authentication Architecture Review

**Date:** 2026-07-11
**Purpose:** Evaluate the stability and correctness of the authentication architecture before advancing to Authorization, Device Trust, and Sync.

## 1. Is the authentication boundary correct?
**No, it is currently too broad.** 
The `AuthRepository` interface encompasses responsibilities that extend far beyond simply verifying identity. It currently orchestrates the entire onboarding pipeline, including biometrics and family creation. Authentication should strictly govern "Who are you?" (Identity) and "Are you active?" (Session). 

## 2. Are interfaces clean?
**They require refactoring.**
While we successfully eradicated `forceDemoLogin` to secure the interface, `AuthRepository` still contains:
- `registerDevice()`
- `setupBiometric()`
- `createFamily()`

These violate the Interface Segregation Principle. `createFamily` strictly belongs to a `FamilyRepository`. `registerDevice` and `setupBiometric` belong in a `DeviceTrustRepository` (which will be relevant for SEC-003).

## 3. Are domain objects stable?
**Partially.**
The `User` entity is overloaded. It currently tracks `authStage` (e.g., `awaitingTwoFactor`, `awaitingBiometrics`). Mixing ephemeral authentication state machine data into the canonical domain `User` entity creates tight coupling. The state machine should ideally operate on a `Session` or `AuthPipelineContext` object until the final `User` identity is minted.

## 4. Are repositories separated correctly?
**No.**
The current architecture forces the DI graph to pass `AuthRepository` into components that only care about device hardware. We must extract:
- `DeviceTrustRepository` (for KeyStore, Biometrics, Device Attestation)
- `FamilyRepository` (for joining, creating, leaving families)

## 5. Is the backend contract future-proof?
**Not yet (Known Blocker B-05).**
Because the backend contract is not finalized, the app currently relies on a monolithic `verifyOtp` signature. A future-proof contract must explicitly support OAuth 2.0 / OIDC flows, specifically allowing for silent JWT refresh rotation via Http Interceptors without surfacing repository calls to the presentation layer.

## 6. Is session lifecycle ownership correct?
**No, it is coupled to the repository.**
`ProductionAuthRepository` directly accesses `SecureStorageService` to read the session. Session lifecycle (Refresh token rotation, expiry detection, offline caching) is a cross-cutting concern. An independent `SessionManager` (or `AuthInterceptor`) should own the lifecycle, providing a stream of authentication states to the router, rather than relying on discrete repository reads.

---
## Review Board Recommendation
Before exiting Phase 2, the `AuthRepository` must be decomposed. However, for the immediate execution of SEC-002 (Authorization), the current decoupled DI boundaries are sufficient, provided SEC-002 focuses strictly on the canonical **Domain Authorization Model** (Family roles) rather than compounding the existing repository interfaces.
